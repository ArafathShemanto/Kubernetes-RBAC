Kubernetes এর RBAC (Role-Based Access Control) আসলে এই তিনটা প্রশ্নের উত্তর। চা নিয়ে বসো। আগে একটা office building এর গল্প বলব, তারপর আসল YAML দেখব, আর শেষে তুমি নিজের হাতে request পাঠিয়ে দেখবে API Server কীভাবে Allowed বা 403 Forbidden বলে।

গল্প

একটা office building এর গল্প

ধরো তুমি নতুন চাকরি পেয়েছ। Office টা একটা বড় building। গেটে একজন security guard বসে আছে, আর সে কাউকে এমনি এমনি ঢুকতে দেয় না। তুমি গেলে সে দুইটা কাজ করে:

  1. ID card দেখে। তুমি আসলেই এই office এর লোক তো? এটা Authentication।
  2. Access list মিলায়। তোমার নামে ৩ তলার file room এ ঢোকার অনুমতি লেখা আছে? এটা Authorization, আর Kubernetes এ এই কাজটা করে RBAC।

Access list টা guard নিজে বানায় না। HR আগে থেকেই দুইটা কাগজ তৈরি করে রাখে: একটা job description (এই পদে কী কী করা যাবে), আর একটা appointment letter (এই job description টা কাকে দেওয়া হলো)। Guard শুধু কাগজ মিলিয়ে দেখে।

কেন দরকার?

RBAC না থাকলে building এ সবার হাতে master key। তার মানে:

  • নতুন intern ভুল করে kubectl delete deployment --all -n prod চালালে production শেষ।
  • একটা Pod hack হলে attacker সেই Pod এর token দিয়ে সব Secret (database password, API key) পড়ে ফেলতে পারে।
  • কে কী করতে পারে, তার কোনো হিসাব থাকে না।

RBAC এর মূল নীতি least privilege: যার যতটুকু দরকার, ঠিক ততটুকু। বেশি না।

ভিতরে কীভাবে কাজ করে?

তুমি kubectl এ যা-ই লেখো, সেটা একটা HTTPS request হয়ে API Server এর কাছে যায়। প্রতিটা request, প্রতিবার, এই গেটগুলো পার হয়:

  1. Authenticationতুমি কে?ভুল হলে 401
  2. Authorization (RBAC)তোমার অনুমতি আছে?না থাকলে 403
  3. AdmissionRequest টা নিয়ম মেনে লেখা? শুধু create, update, delete এ লাগে।
  4. etcdCluster এর খাতা। এখানে লেখা হয়, এখান থেকে পড়া হয়।
মনে রাখো
  • RBAC এ শুধু allow লেখা যায়। Deny বলে কোনো rule নেই। কিছু লেখা না থাকলে উত্তর "না"।
  • Permission যোগ হয়। দুইটা Role পেলে দুইটারই সব permission পাবে। একটা Role দিয়ে আরেকটার permission কাটা যায় না।
  • 401 আর 403 আলাদা। 401 মানে guard তোমাকে চেনেই না। 403 মানে চেনে, কিন্তু অনুমতি নেই।

Step 1

Subject: permission টা কে পাবে?

Subject মানে "কে"। Kubernetes তিন রকম Subject চেনে।

User · একজন মানুষ

তুমি, আমি, alice। মজার ব্যাপার, Kubernetes এ User নামে কোনো object নেই। kubectl get users কাজ করে না। User আসে বাইরে থেকে: certificate এর CN field, company SSO (OIDC), বা cloud IAM। API Server শুধু নামটা বিশ্বাস করে।

- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
Group · মানুষের দল

এক এক জনকে আলাদা করে permission দিলে পাগল হয়ে যাবে। তাই developers বা sre নামে Group কে permission দাও। Group ও বাইরে থেকে আসে (certificate এর O field, SSO এর groups)। কিছু Group built-in, যেমন system:authenticated, মানে login করা সবাই।

- kind: Group
  name: developers
  apiGroup: rbac.authorization.k8s.io
ServiceAccount · machine এর ID card

Pod, CI/CD pipeline, operator, এরা তো মানুষ না। এদের জন্য ServiceAccount। এটা আসল Kubernetes object, আর একটা namespace এর ভিতরে থাকে। Pod চালু হলে তার ভিতরে একটা token বসে যায়, সেই token দিয়ে Pod API Server কে request পাঠায়। পুরো নাম: system:serviceaccount:dev:app-bot

- kind: ServiceAccount
  name: app-bot
  namespace: dev
মনে রাখো

মানুষ = User বা Group। Machine = ServiceAccount। Pod এ কোনো ServiceAccount না বললে সে namespace এর default ServiceAccount পায়, যার বলার মতো কোনো permission নেই (আর না থাকাই ভালো)।

একটু গভীরে: system:masters Group

এই Group এর লোক RBAC check ছাড়াই সব কিছু করতে পারে। কারো certificate এ এটা দিও না। দিলে পরে আর ফেরত নেওয়ার সহজ উপায় থাকে না, কারণ certificate বাতিল করা কঠিন।

Step 2

Role আর ClusterRole: কী কী করা যাবে?

Role হলো job description। এখানে কারো নাম থাকে না, শুধু কাজের list থাকে। প্রতিটা লাইনকে বলে rule, আর একটা rule এ তিনটা জিনিস:

rules:
- apiGroups: [""]                  # কোন API group
  resources: ["pods"]              # কোন জিনিস
  verbs: ["get", "list", "watch"]  # কী করতে পারবে
  • apiGroups: Resource টা কোন API group এর। "" (খালি string) মানে core group: pods, services, configmaps, secrets। Deployment থাকে apps group এ।
  • resources: কোন জিনিস। সব সময় plural আর ছোট হাতের: pods, deployments।
  • verbs: সেই জিনিসের উপর কী করা যাবে। নিচের table টা দেখো।
Verbমানেkubectl এHTTP
getএকটা নির্দিষ্ট জিনিস দেখাkubectl get pod web-1GET (নাম সহ)
listসবগুলো একসাথে দেখাkubectl get podsGET
watchLive পরিবর্তন দেখাkubectl get pods -wGET ?watch
createনতুন বানানোkubectl create -fPOST
updateপুরোটা বদলানোkubectl replace -fPUT
patchকিছু অংশ বদলানোkubectl patchPATCH
deleteমুছে ফেলাkubectl delete pod web-1DELETE

কোন resource কোন group এ, আর সেটা namespace এর ভিতরে কিনা, এক command এ দেখা যায়: kubectl api-resources

list কে হালকা ভেবো না। list secrets থাকলে সব Secret এর ভিতরের value ও পড়ে ফেলা যায়, শুধু নাম না।

Role নাকি ClusterRole?

Role · এক namespace

একটা namespace এর ভিতরে কাজ করে। metadata.namespace দিতে হয়। Office এর ভাষায়: শুধু ৩ তলার job description।

ClusterRole · পুরো cluster

কোনো namespace এর না। তিনটা কারণে লাগে:

  • Cluster-scoped resource এর জন্য, যেমন nodes, namespaces, persistentvolumes। এগুলো কোনো namespace এ থাকে না।
  • সব namespace এ একই permission দিতে।
  • একবার লিখে অনেক namespace এ reuse করতে, template এর মতো।

Kubernetes কিছু ClusterRole আগে থেকেই দিয়ে রাখে: view, edit, admin, cluster-admin। নতুন কিছু লেখার আগে দেখো এগুলো দিয়ে কাজ হয় কিনা।

একটু গভীরে: subresource আর resourceNames

pods/log (log পড়া) আর pods/exec (Pod এর ভিতরে ঢোকা) আলাদা resource। pods এ permission থাকলেই log পড়া যায় না, pods/log আলাদা করে দিতে হয়। আর resourceNames: ["app-config"] দিলে শুধু ওই একটা object এ permission পড়ে।

Step 3

RoleBinding আর ClusterRoleBinding: কাকে দেওয়া হলো?

Role নিজে কিছু করে না। কাগজটা drawer এ পড়ে থাকলে কারো কোনো permission হয় না। Binding হলো সেই কাগজটা কারো হাতে তুলে দেওয়া। Binding এ দুইটা অংশ:

  • subjects: কাকে দিচ্ছি। User, Group বা ServiceAccount। একসাথে অনেকজনও হয়।
  • roleRef: কোন Role বা ClusterRole দিচ্ছি। একটাই।

আর Binding কোন ধরনের, তার উপর নির্ভর করে permission টা কোথায় কাজ করবে। নিচে চারটা জোড়া, আর প্রতিটায় permission কোথায় পৌঁছায়।

Role+RoleBinding (dev)
devprodnodes

শুধু ওই এক namespace এ। সবচেয়ে বেশি এটাই ব্যবহার হয়।

ClusterRole+RoleBinding (dev)
devprodnodes

ClusterRole টা এখানে template। কাজ করবে শুধু RoleBinding এর namespace এ। Cluster-scoped resource (nodes) এভাবে পাওয়া যায় না।

ClusterRole+ClusterRoleBinding
devprodnodes

সব namespace আর cluster-scoped resource। সাবধানে দাও।

Role+ClusterRoleBinding
হয় না

API Server reject করে। ClusterRoleBinding শুধু ClusterRole ধরতে পারে।

সহজ করে বললে

Role ঠিক করে কী। Binding এর subjects ঠিক করে কে। আর Binding এর ধরন ঠিক করে কোথায়।

  • roleRef একবার লিখলে আর বদলানো যায় না। বদলাতে হলে Binding delete করে নতুন বানাতে হয়।
  • নিজের চেয়ে বেশি permission কাউকে দেওয়া যায় না। যে permission তোমার নিজের নেই, সেই Role তুমি বানাতে বা bind করতে পারবে না। এতে ঘুরিয়ে নিজের permission বাড়ানো আটকায়।

Step 4

YAML এ লেখা

এবার আসল জিনিস। alice কে dev namespace এ Pod দেখার অনুমতি দেব। দুইটা object লাগবে: একটা Role, একটা RoleBinding।

rbac.yaml
# ১) Job description: কী কী করা যাবে
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: dev            # শুধু dev namespace এ
rules:
- apiGroups: [""]           # core group, pods এখানে
  resources: ["pods"]
  verbs: ["get", "list", "watch"]
---
# ২) Appointment letter: কাকে দেওয়া হলো
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: alice-read-pods
  namespace: dev
subjects:                   # কে পাবে
- kind: User
  name: alice
  apiGroup: rbac.authorization.k8s.io
roleRef:                    # কোন Role
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io

চালাও আর পরীক্ষা করো:

terminal
kubectl apply -f rbac.yaml

kubectl auth can-i list pods -n dev --as alice      # yes
kubectl auth can-i delete pods -n dev --as alice    # no, delete verb নেই
kubectl auth can-i list pods -n prod --as alice     # no, অন্য namespace
Pod এর জন্য একই জিনিস (ServiceAccount)

তিনটা ধাপ: ServiceAccount বানাও, RoleBinding এর subject এ সেটা দাও, আর Pod এর spec এ তার নাম লেখো।

app-bot.yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-bot
  namespace: dev
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-bot-read
  namespace: dev
subjects:
- kind: ServiceAccount        # এখানে apiGroup লাগে না
  name: app-bot
  namespace: dev
roleRef:
  kind: Role
  name: app-reader            # pod-reader এর মতোই আরেকটা Role
  apiGroup: rbac.authorization.k8s.io
---
apiVersion: v1
kind: Pod
metadata:
  name: app
  namespace: dev
spec:
  serviceAccountName: app-bot # Pod এই ID card নিয়ে চলবে
  containers:
  - name: app
    image: nginx

পরীক্ষা: kubectl auth can-i list pods -n dev --as system:serviceaccount:dev:app-bot

পুরো cluster এর জন্য (ClusterRole + ClusterRoleBinding)

sre Group এর সবাই সব namespace এর Pod আর Deployment দেখতে পারবে, সাথে Node ও।

sre-view.yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: cluster-viewer        # namespace নেই
rules:
- apiGroups: [""]
  resources: ["pods", "nodes"]
  verbs: ["get", "list", "watch"]
- apiGroups: ["apps"]
  resources: ["deployments"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: sre-view
subjects:
- kind: Group
  name: sre
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: ClusterRole
  name: cluster-viewer
  apiGroup: rbac.authorization.k8s.io

হাতে-কলমে

নিজের হাতে request পাঠাও, guard কে কাজ করতে দেখো

নিচে একটা ছোট cluster আছে: তিনজন Subject, চারটা Binding, চারটা Role। একটা scenario বেছে নাও, তারপর সামনে চেপে চেপে দেখো request টা কোথায় যায় আর API Server কী কী মিলায়।

Scenario বেছে নাও

কাজের সময়

আটকে গেলে: 403 debug করার command

terminal
kubectl auth whoami                       # API Server আমাকে কী নামে চেনে?
kubectl auth can-i delete pods -n dev     # আমি কি এটা করতে পারি?
kubectl auth can-i --list -n dev          # dev এ আমার সব permission
kubectl describe role pod-reader -n dev   # Role এ আসলে কী লেখা
kubectl get rolebindings,clusterrolebindings -A -o wide | grep alice   # alice কোথায় bind করা

403 এর error message টা মন দিয়ে পড়ো। ওখানেই লেখা থাকে কে, কোন verb, কোন resource, কোন API group, কোন namespace। এই পাঁচটার একটা তোমার Role বা Binding এর সাথে মিলছে না।

Production এ যে ভুলগুলো সবাই করে

  • সবাইকে cluster-admin দিয়ে দেওয়াকাজ চলছে বলে রেখে দিও না। Namespace এর ভিতরে edit বা নিজের লেখা Role দাও।
  • verbs: ["*"] আর resources: ["*"] লেখাআজ যা আছে শুধু তা না, কাল যে নতুন resource আসবে তারও permission দিয়ে দিলে।
  • default ServiceAccount এ permission দেওয়াওই namespace এর সব Pod সেই permission পেয়ে যায়। প্রতিটা app এর আলাদা ServiceAccount বানাও।
  • Secret এর get, list, watch হালকাভাবে দেওয়াSecret পড়তে পারা মানে password পড়তে পারা।
  • create pods কে নিরাপদ ভাবাযে Pod বানাতে পারে, সে ওই namespace এর যেকোনো Secret বা ServiceAccount নিজের Pod এ mount করে নিতে পারে।

এক নজরে

Subject = কে। Role = কী। Binding = দুইটাকে জোড়া লাগানো।
Role আর RoleBinding = এক namespace। ClusterRole আর ClusterRoleBinding = পুরো cluster।
শুধু allow লেখা যায়। কিছু লেখা না থাকলে deny। Permission যোগ হয়।
401 = guard চেনে না। 403 = চেনে, অনুমতি নেই।
পরীক্ষা করার command: kubectl auth can-i
roleRef বদলানো যায় না। নতুন Binding বানাতে হয়।
উদাহরণের নামগুলো (alice, bob, app-bot) বানানো। Terminal এর output নমুনা, তোমার cluster এ নাম আর সংখ্যা আলাদা হবে।
